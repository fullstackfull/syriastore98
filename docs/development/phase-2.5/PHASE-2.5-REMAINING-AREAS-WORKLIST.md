### Why a shared dev server made parallel live measurement unsafe

Ten areas were audited in parallel against one checkout. A live pass cannot be parallelised the same way, for four reasons that are specific to this codebase, not generic caution:

1. **Tenant context is global to the session, and silent when absent.** `config/tenancy.php` sets `null_tenant => 'open'`, so when no tenant resolves the scope adds no predicate — an agent switching store context changes what another agent's screen renders with no visible cue and no error.
2. **Theme and locale are stored settings, not per-request.** `dir` comes from `$setting['SITE_RTL']` (`layouts/app.blade.php:85`) and the body colour class from the settings read at `app.blade.php:42-57`. One agent flipping to Arabic or to dark mode re-renders every other agent's screenshots — and the dark/light arm is exactly what half the colour findings turn on. The audit's own refutation of `app.blade.php:374` shows how easily the wrong arm gets attributed.
3. **Table state persists per browser.** `buildDataTable()` ships `stateSave` with `ss-colvis` and `ss-density`, so one agent's column or density choice changes another agent's table screenshot — on the very tables §2 is about.
4. **79 of 95 models are `Cachable`, and several handlers read the platform admin through `Cache::remember('admin_details', 3600, …)`.** A fixture one agent writes is served stale to another; this repository has three measured false readings from exactly that mechanism, and under `CACHE_STORE=array` the stale row survives for the rest of the run.

A live pass therefore has to be **serialised one area at a time with locale, theme and tenant pinned per run, and `Cache::forget('admin_details')` between fixture and request** — or given one dev server and one browser profile per agent. The cheapest sequencing is to run it per wave, immediately after that wave's edits, rather than as one global verification pass.
