## 3. Exact outstanding blockers — all ten

None is a capture gap, and none can be closed by more engineering effort on this branch alone.
Grouped by what actually blocks them:

### 3.1 Four surfaces need a MySQL fixture (4 rows)

`Customer report body`, `Sales report body`, `Sales report bar body`, `Top Sales Report`.

Each answers **HTTP 500 on the SQLite dev fixture in all four combinations**, because the handler
builds raw SQL with functions SQLite does not implement — `MONTH()` and `YEAR()`
(`ReportController::reports_chart`, `::order_reports_chart:720`, `::order_reports_chart_data:985`)
and `SUBSTRING_INDEX` (`::top_product:2814`). **Production is MySQL, so these are almost certainly
fine in production and cannot be shown to be from here.** Closing them needs a MySQL dev fixture,
which is a tooling package, not a UI one. This is the same class of blindness that let P01-SEC-13
survive, and `CLAUDE.md` already records SQLite's type affinity as a known hazard.

### 3.2 Two need a connected external store (2 rows)

`Shopify import screens` and `WooCommerce import screens`. Measured HTTP 200 with an **empty body
and no `<html>` element** in all four combinations: the controllers require a connected store's
settings before rendering anything. Neither can be driven without live third-party credentials.

### 3.3 One cannot be rendered under `flutter_test` (1 row)

`Invoice (PDF build) / Invoice viewer`. `PdfPreview` rasterises through the `printing` plugin and
the capture raises `MissingPluginException`. The viewer **chrome** is captured; the PDF **body** is
not.

### 3.4 One is inactive code, not an unreachable screen (1 row)

`COD / Stripe / Bank-transfer gateway editors`. Measured: all six files are **100% commented out —
815 lines, 0 live**. There is no screen to redesign.

### 3.5 Two are registered but unimplemented, and need an owner decision (2 rows)

* **`Edit customer (registered, unimplemented)`** — not a missing screen but a **web/Flutter parity
  gap**. The web routes are deliberately not registered (`routes/web.php:1191` excludes
  `edit`/`update`, applied after `GET /customer/1/edit` answered HTTP 500), while a complete
  customer-update backend ships and the Flutter admin already uses it (`routes/api.php:267`
  → `DashboardController::updateCustomerInfo`). Building the web screen is **new merchant
  functionality**, which this phase is not authorised to add.
* **`Wishlist create / edit / store / update`** — four routes resolve and none renders a byte;
  `WishlistController::create()` and `::store()` have bodies that are literally `//`.

### 6.2 Human security checks that remain outstanding

* **Incident P1-SEC-40 (#120) — the database dump exposure — is NOT remediated by any UI work in
  this phase**, and `CLAUDE.md` records that explicitly. It is coordinated separately.
* **`APP_KEY` is in git history and unrotated**, so `Crypt::encrypt()` is an encoding and not a
  control. Every encrypted id in a URL — including the order and receipt ids this wave drove — is
  forgeable. A recorded finding, not a new one.
* **Sanctum tokens never expire** and every one carries `['*']`; there is no refresh path for any
  client. See `docs/security/P01-TOKEN-EXPIRY-PROPOSAL.md` before touching it.
* **The scoped operator authorization change is written out and NOT made.** Per the owner's
  instruction, `docs/security/P0-USER-DELETION-CASCADE.md` §8.1 specifies exactly one
  `platform-operator` Laratrust role carrying `Edit User` and nothing else, for approval. Operator
  least privilege is pinned by `test_an_operator_without_edit_user_may_not_update_anyone`, which
  fails on a reorder.
* **Store deletion remains a functional limitation, not a feature.** §8.3 of the same document:
  `DELETE stores/{store}` is disabled, and disabling is not solving. There is no safe way for an
  operator to retire a store or an account.
* **The language editor's save path answers HTTP 500 for any locale with PHP translation files,
  and there is a latent arbitrary-`.php`-write behind it.** Queued as **P25-SEC-02**. Two separate
  facts, and keeping them apart matters:
  * `storeLanguageData()` writes `file_put_contents($langFolder . "/" . $fileName . '.php', …)`
    where `$fileName` is an **array key from the request body**, unsanitised —
    `message[../../../../public/x]` would write an attacker-chosen PHP file. **Not reachable**:
    `buildArray()` is defined nowhere in the repository, so `Illuminate\Routing\Controller::__call`
    throws first, measured.
  * **The exception is reachable** through the product's own form:
    `language/index.blade.php:142-159` emits `message[…]` inputs for every PHP translation file a
    locale has, and **38 ship**. So an operator saving `pt-br` or `pl` gets a 500, every time.
  * Both are **operator-only** — `Create Language` is denylisted in
    `config/superadminaccess.php:9`, enforced by `RolePolicy::isGrantableBy()` on the write path.
  * **Not fixed in this wave on purpose:** repairing the 500 *means* implementing `buildArray()`,
    which is the one change that arms the write, on an operator feature that generates executable
    PHP. A named warning sits at the exact line instead, saying that the dangerous change here is
    the helpful-looking one.

* **Twelve controller view literals do not resolve**, found while chasing one of them. One
  (`product.sku_combinations`) is settled and classified; **the other eleven are not** — the census
  ran with 0 add-ons active, so each needs a per-view reachability check before it is called a
  defect. Written out in `PHASE-2.5-REMAINING-AREAS-WORKLIST.md` so the next person starts from a
  measurement.

### 6.3 What the seven closure checks of §2 showed

All seven map onto **92 passing cases across six classes**, each on a disposable `:memory:`
database. The mapping table is `docs/security/P0-USER-DELETION-CASCADE.md` §8.4. The verification
found a **new defect in itself**: three of the four user-management paths compared
`$target->type === 'super admin'` with a literal, which MySQL's `utf8mb4_unicode_ci` treats as equal
to `'Super Admin'` and `'super admin '` while PHP's `===` does not. `update()`, `resetPassword()`
and `impersonate()` now go through the shared normalising helper. That is a tightening, not a
reorder.

## 7. One owner decision this wave did not take

`POST products/sku_combination` has **no caller anywhere** (0 hits across `resources/`, `public/`,
`packages/`) **and its view does not exist** in the repository, so it would answer HTTP 500 rather
than a fragment if anything called it. This corrects the record at `routes/web.php:1016-1029`, which
kept the route on the stated grounds that "its method exists, so it does not 500" — the method does,
its view does not.

**Removing a route is a contract change this phase is not authorised to make**, so it stays, is
classified OUT OF SCOPE with both measurements, and is named here as a one-line decision whenever
the owner wants it taken. Nothing a merchant can reach is affected either way.
