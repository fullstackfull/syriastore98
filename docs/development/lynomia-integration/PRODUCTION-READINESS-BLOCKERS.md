# Store Syria × Lynomia — tracked production-readiness blockers

**One register, carried forward across phases.** Each completion report had its own "known
limitations" section, which is the right place to record what a phase found but the wrong place
to track what is still open: a blocker raised in Phase 1 and still open in Phase 5 appears in
five documents, with no single answer to "what is stopping go-live today".

This file is that answer. It is updated at the end of every phase, and each entry carries the
phase that raised it, the phase that closed it if any, and **who can close it** — because the
most important property of these entries is that most of them cannot be closed from inside
these two repositories at all.

Status at: **Phase 5 complete, including P5H hardening.** Phase 4 closed and pushed
(Lynomia `88630724`, Store Syria `152888c4`); Phase 5 pushed on both branches (Lynomia through
`3331d245`, Store Syria through `b9b49501`).

## A. OPEN — nothing in these repositories can close these

### A1. No run against a live Lynomia has ever happened

| | |
|---|---|
| Raised | Phase 1, restated every phase since |
| Closes by | A staging deployment of both sides, by the owner |
| Severity | **The single largest unknown.** Everything else here is bounded; this is not. |

Every test in both repositories, and every browser harness, runs against the other side's
contract *as this work understands it*. The contract is pinned by specs on the Lynomia side and
by a scriptable fake (`tests/Feature/Lynomia/InteractsWithLynomia.php`) on the Store Syria side.
Both were written from the same reading of the same code, which is exactly why they agree — and
agreement between two expressions of one reading is not evidence that the reading is right.

**Phase 5 stopped arguing this in the abstract.** An adversarial review at the end of it found
FOUR features that passed every test on both sides and could not have worked against a real
deployment, each because the fake and the code shared one mistake:

| What was broken | How the fake hid it |
|---|---|
| Store Syria sent a bare store id where Lynomia holds `{installation_ref}:{id}` — so every checkout opt-in was rejected 404, every inbound consent event was dropped, reconciliation repaired nothing, and every store-scoped count answered account-wide | every audience and consent fixture used the bare id on both sides of itself, while the module's own commerce test asserted the prefixed form |
| Campaign cancellation 500'd for every caller | only a model-level spec existed; nothing exercised the route |
| A campaign was never marked as its installation's | the preview sent the field and the create did not, and no test compared them |
| A shopper who opted in at checkout could never be a campaign recipient | the audience fixtures granted NATIVE consent, which is not what a checkout opt-in produces |

Two of the four are now covered by cross-repository artifacts (`consent_changed.v1.json` and
`audience_fields.v1.json`, byte-identical and SHA-pinned in both repositories). **The rest of
the surface is not.** A staging run is the only thing that finds the next one, and the base
rate this phase established is four in one phase.

**What a staging run must cover,** in this order, because each step is a prerequisite for the
next:

1. Provision a workspace from Store Syria and complete the SSO handoff (Phase 1).
2. Open the native inbox, send and receive on a real channel (Phase 2).
3. Connect a store, push a commerce event, see it in an agent's panel (Phase 3).
4. Build, publish and run one flow per starter template on a test WhatsApp number (Phase 4).
5. Capture a consent at checkout, watch it reach Lynomia, withdraw it on WhatsApp and watch
   the withdrawal come back; then run a campaign and confirm the withdrawn shopper is skipped
   with the recorded reason, and that the quota decremented (Phase 5).

**Phase 5 narrowed this blocker without closing it.** The cross-repository contract test
(Lynomia `spec/contracts/consent_changed_contract_spec.rb`, Store Syria
`tests/Contract/LynomiaConsentContractTest.php`) now proves the two codebases agree about the
wire format, the identity fields, the signature construction, the ordering key and the refusal
semantics — using **one artifact generated by the real producer** and replayed through the
**real ingress route**, with a shared SHA256 so neither side can change it alone. That removes
"the two sides disagree about the payload" from the list of things a staging run might
discover. It leaves DNS, TLS, real credentials, Sidekiq actually delivering, clock skew
between two hosts, and a webhook subscription that was never created upstream — which is what
A1 is now about.
5. Run the four browser harnesses against the *deployed* pages rather than rendered fixtures
   (`tests/Browser/run.sh`, pointed at the staging host via `STUDIO_BASE`).
6. Confirm the consent gate refuses a promotional send to a contact with no grant (Phase 3/5).
7. Phase 5's own additions, listed in the Phase 5 report when it is written.

### A2. `APP_KEY` was published and has not been rotated

| | |
|---|---|
| Raised | Pre-Phase-1; recorded in `docs/security/SECRET-ROTATION-CHECKLIST.md` |
| Closes by | The owner, following that checklist |
| Severity | High, and **accepted** as an operational blocker rather than an authorization to bypass security |

The practical consequence for this integration, and the reason it is named in
`packages/workdo/LynomiaChat/src/config/lynomia.php` at the top of the file: Laravel's
`encrypted` cast derives its key from `APP_KEY`, so an encrypted column protects nothing in this
installation. That is why **no credential introduced by Phases 1–5 is stored in the database at
all** — the platform token is read from the environment per use, per-person Lynomia bearers are
cached in an `array` store that does not outlive the request, and each store's webhook secret is
derived by HMAC from a master secret rather than stored.

That is the only mitigation available from inside this scope. It does not close the blocker.

### A3. GATE F — 15 tables that live code reads and writes have no migration

| | |
|---|---|
| Raised | Pre-Phase-1; `database/migrations/_gate_f_pending/README.md` |
| Closes by | The owner, with `SHOW CREATE TABLE` output from production |
| Severity | High for financial work; **not on the Lynomia integration's critical path** |

Six of the fifteen are money-bearing. The provisional drafts are held out of the live migration
path deliberately and by two independent mechanisms, because a guarded migration (`Schema::hasTable`)
is safe when its definition is right and a silent trap when it is a guess — a provisional
definition that created a table first would make the later correct one a no-op, and the wrong
column types would become permanent and invisible.

Phase 4's financial fix did not change this and its test file asserts the tables are still
absent, so the limit stays visible rather than decaying into folklore.

### A4. Store Syria is PRE_UAT for cart recovery

| | |
|---|---|
| Raised | Phase 3 (`Commerce::Switches::PRE_UAT[:recovery]`) |
| Closes by | A reviewed code change after provider UAT, **not a setting** |
| Severity | Medium — it correctly withholds a capability rather than failing one |

This is working as designed and is listed here so it is not mistaken for a defect. Phase 4's
automation vocabulary reports the cart trigger as unavailable with reason
`recovery_unavailable` rather than offering a rule that would silently never fire. Any Phase 5
campaign type that depends on abandoned carts inherits the same restriction and must report it
the same way.

### B2. Phase 5's own blockers — CLOSED, retained here as a pointer to §C

The final verification pass confirmed 19 residual holes and closed eleven. The owner
directed that the remaining eight and the capability gap be closed before the next
integration phase opened. **All nine are closed**, and each fix was proved by reverting it
and watching the new coverage go red. They are recorded under §C as C6–C14.

Closing them produced a **third adversarial round**, run against the second round's fixes:
67 agents, 42 verdicts, **15 findings survived verification — every one of them in code
written during this verification pass**, 13 in the two commits immediately preceding it. All
15 are fixed. `PHASE-5-COMPLETION-REPORT.md` §10 carries them.

**The warning recorded here about B2.1 was real, and is kept because it is the reason the
fix is shaped as it is.** `Partners::Eligibility` has two expressions of the same rule:
`refusal`, asked per recipient at the send boundary, and `filter`, which resolves the
audience. Only `refusal` called `subject_of?`. Adding a `Commerce::CustomerLink` check to
`subject_of?` alone would have made the boundary refuse contacts the audience still
selected — **the audience WIDER than the send**, a campaign reporting it reached people it
refused, which is worse than the over-inclusion B2.1 described and is the one direction that
pair exists to prevent. Both expressions were changed together, and the agreement example in
`spec/models/campaign_partner_audience_spec.rb` would not have caught a divergence as it was
written: every contact in its population was of the campaign's own account, so the subject
check was true for all of them. Two customer-linked members were added to that population
first — one linked only to the account's other store, and one linked to both — which is the
pair that separates "not linked to a different store of this account" from "has a link to
this store".

Neither is a Phase 5 regression. Both are pre-existing, both were found by the fourth
adversarial round reading code rather than by any failure, and both are recorded here rather
than fixed because the fix is a policy decision. `PHASE-5-COMPLETION-REPORT.md` §10.4 has
the round.

| # | Severity | What | Where | Closes by |
|---|---|---|---|---|
| B3.1 | **Medium–high** | **A third outbound surface asks nothing about consent.** An agent picking a WhatsApp template in the composer — or opening a brand-new conversation with one — reaches `Whatsapp::SendOnWhatsappService#send_template_message` with no eligibility call anywhere on the path, and the picker offers MARKETING templates (`isSendableTemplate` excludes only AUTHENTICATION and CSAT). ### B4. There is no verified merchant phone number in Store Syria

Raised by P6E, which needs one and refuses to proceed without it.

| | |
|---|---|
| Raised | Phase 6 (P6E) |
| Severity | Medium — it makes a delivered capability unusable for some merchants, and would be high if P6E guessed instead of refusing |
| Closes by | A merchant-facing verification of their own number, and a repair of the two writers below |

`users.mobile` is the only place a merchant's phone number lives. It is nullable, not unique,
not indexed, and has no format rule — the web profile form and the API both accept any string
up to 20 characters. There is no OTP, no `phone_verified` flag and no KYC for a merchant
number anywhere in the repository; a search for every spelling of a verification flag returns
nothing.

It is also actively written with values that are not phone numbers:

| Writer | What it writes |
|---|---|
| self-registration | `''` rather than NULL |
| `app/Http/Controllers/StoreController.php:268` | the literal `7878787878` |

**Why this is recorded rather than worked around.** A WhatsApp message to a number like that
does not fail safely. It reaches whoever actually holds that number — a stranger — with a
notice about a merchant's account. So `PlatformRecipients` admits only a number it can
normalise to an international form and that is not a known placeholder, and records any
merchant it cannot address as unreachable with the reason.

**The consequence, stated plainly.** Platform communications work, and a merchant whose
number was never recorded properly simply cannot be reached by them. Every merchant created
through Super Admin store creation is in that set today. The Super Admin notices tab shows
the refusals and their reasons, so the gap is visible rather than silent, but it is a gap.

**What would close it.** Verification the merchant performs themselves — the number is only
trustworthy if its holder proved it — plus correcting the two writers so the column stops
accumulating values that were never anybody's number.

## D. Standing restrictions — not blockers, and not to be "resolved"

These are deliberate and stay in force until the owner lifts them explicitly. They are listed
so that a later phase does not read them as oversights and close them.

- `LYNOMIA_INTEGRATION_ENABLED` defaults **false**. Nothing performs a remote call while false.
- `LYNOMIA_COMMERCE_EVENTS_ENABLED` defaults **false**, and while off **nothing is recorded**
  rather than recorded and held.
- `.env`, `APP_KEY` and production credentials are not modified by any phase.
- No live communication-provider account is connected; no production messaging is activated.
- Nothing is merged or deployed.
- The per-person Lynomia credential cache defaults to the `array` store, which is not a cache —
  it costs one extra call per merchant request and is the right default, because this
  installation's default cache driver is `file` and any other default would write a live bearer
  to disk in plaintext.
