# PHASE 7 — STAGING AND LAUNCH READINESS PLAN

**Status: PROPOSED. Awaiting owner approval. Nothing in this document has been executed.**

No step here was performed during the post-Phase-6 hardening. Production was not touched, no
provider was connected, no WhatsApp message was sent, no charge was created, and neither
`.env` nor `APP_KEY` was altered in either repository. The plan stops at the point where an
owner decision is required, which is before the first byte crosses between two real hosts.

| | |
|---|---|
| Scope | the Store Syria × Lynomia Chat integration, Phases 1–6 plus the post-Phase-6 hardening |
| Branches | `claude/store-syria-lynomia-integration-1oa1tt` in both repositories |
| Precondition | Phase 6 accepted as development-complete; B4 mechanism built; the delivery feed built and contract-pinned |
| What Phase 7 is | the first execution of this integration against two real, non-production deployments |
| What Phase 7 is not | a production release. §15 says what a production decision would additionally require |

## 0. Why this phase exists, stated plainly

Everything built across six phases has been verified against *the other side's contract as
this work understands it*. That is a strong form of verification and it is not the same as
evidence. The project has now twice produced features that passed every test on both sides
and could not have worked against a real deployment:

| When | What was green and still broken |
|---|---|
| Phase 5 audit | four features, each because the fake and the code shared one mistake — a bare store id where Lynomia holds `{installation_ref}:{id}`, a cancel route nothing exercised, a field the preview sent and the create did not, and audience fixtures granting a consent shape checkout never produces |
| Post-Phase-6 | the delivery feed shipped with **no webhook subscription on the platform workspace**. Twenty-five examples passed because every one of them posted to the ingress directly. In a real deployment Lynomia would never have called it |

The second of those is worth dwelling on, because blocker A1 predicted it in writing — "a
webhook subscription that was never created upstream" — and it still shipped. A1's estimate of
its own base rate is therefore not pessimistic. **Phase 7 is the control that finds the next
one**, and the plan below is ordered so that each step is a prerequisite for the next rather
than a checklist that can be sampled.

Two cross-repository contract artifacts now remove a specific class of surprise from that
list — `consent_changed.v1.json` and `message_delivery_status.v1.json`, each generated by the
real producer, committed byte-identically in both repositories and SHA-guarded on both sides.
They prove the wire format, the vocabulary, the identity fields, the ordering key and the
refusal semantics. They prove nothing about DNS, TLS, real credentials, Sidekiq actually
delivering, clock skew between two hosts, or a subscription nobody created.

## 1. Non-production environment architecture

Two deployments, isolated from production in every dimension that can carry data or money.

```
            ┌────────────────────────────┐        ┌────────────────────────────┐
            │  STORE SYRIA (staging)     │        │  LYNOMIA CHAT (staging)    │
            │  Laravel 11 / PHP 8.3      │        │  Rails 7.2 / Ruby 3.4.4    │
            │                            │        │                            │
  operator →│  Super Admin console       │        │  Super Admin console       │← operator
  merchant →│  merchant dashboard        │        │  agent dashboard           │← agent
            │                            │        │                            │
            │  MySQL (own instance)      │        │  Postgres (own instance)   │
            │  Redis (own instance)      │        │  Redis (own instance)      │
            │  queue worker + scheduler  │        │  Sidekiq + scheduler       │
            └────────────┬───────────────┘        └──────────────┬─────────────┘
                         │                                       │
                         │  platform token, server-to-server     │
                         │  POST/GET https://lynomia.staging/... │
                         ├──────────────────────────────────────►│
                         │                                       │
                         │  account webhooks, HMAC-signed        │
                         │◄──────────────────────────────────────┤
                         │  POST /lynomia/events/{store}         │
                         │  POST /lynomia/platform-events        │
```

### 1.1 Hard requirements

| # | Requirement | Why it is not optional |
|---|---|---|
| 1.1.1 | Separate database instances from production, not separate schemas on the same server | a staging misconfiguration that points at production data is the failure mode this phase is most likely to produce, and a schema boundary does not survive a wrong `DB_DATABASE` |
| 1.1.2 | Separate Redis instances | both sides use Redis for queues, locks and rate limits; a shared instance lets a staging sweep consume a production lock |
| 1.1.3 | Both reachable over **public HTTPS with real certificates** | the webhook direction is Lynomia → Store Syria. A tunnel or a self-signed certificate changes the TLS path being tested, which is one of the things A1 is explicitly about |
| 1.1.4 | Distinct hostnames that cannot be confused with production at a glance | the operator will be typing these under time pressure |
| 1.1.5 | A WhatsApp number dedicated to staging, **not** a production number | Meta quality ratings are per number and a UAT run can damage one |
| 1.1.6 | Stripe (or whatever billing provider is configured) in **test mode**, with test keys | §11 exercises quota and entitlement, not payment capture |
| 1.1.7 | Both hosts' clocks synchronised by NTP | the webhook signature has a 300-second tolerance (`LYNOMIA_WEBHOOK_TOLERANCE_SECONDS`); clock skew between two hosts is a named A1 unknown and §12.4 measures it deliberately |
| 1.1.8 | Store Syria's scheduler actually running (`schedule:run` every minute) | five module commands depend on it, including the two reconciliation sweeps. A deployment without a scheduler passes §4–§10 and fails silently in §12 |
| 1.1.9 | Lynomia's Sidekiq actually running, with the webhook queue drained | `WebhookJob` is how every event leaves Lynomia |

### 1.2 Data

Staging carries **synthetic merchants, synthetic shoppers and synthetic orders only**. No
production customer record, order, phone number or email is copied in. The one exception
requiring an explicit owner decision is §9: a real WhatsApp send needs a real handset, and
that handset's number belongs to a person who must consent to receiving test messages.

### 2.3 Credential handling during the window

1. The platform token is generated in Lynomia Super Admin and typed directly into Store
   Syria's staging environment. It is **not** pasted into a ticket, a chat, this document, or
   a shell history that is retained.
2. `LYNOMIA_WEBHOOK_MASTER_SECRET` is generated on the Store Syria host
   (`openssl rand -hex 32`) and never leaves it. Lynomia never holds it: Store Syria *chooses*
   the per-webhook secret when it registers a subscription and recomputes it on the way in.
3. Both are rotated after Phase 7, before any production use, because a staging credential
   has been handled by more people than a production one should be.
4. `docs/security/SECRET-ROTATION-CHECKLIST.md` is the procedure.

**GO/NO-GO 2.A** — the owner confirms the staging hosts, the dedicated WhatsApp number and
the test-mode billing keys exist and are not production. No step past here runs otherwise.

## 12. Failure, retry and recovery scenarios

Deliberate breakage. Each one is restored before the next.

| # | Scenario | Expected |
|---|---|---|
| 12.1 | Lynomia returns 503 for 2 minutes | Store Syria retries writes per its ladder; **reads are not retried across a timeout** (a read timeout means the answer was lost, and retrying a send posts a second reply a merchant never wrote) |
| 12.2 | Lynomia's TCP connection is dropped mid-send of an operational notice | the notice is `indeterminate` / `unknown`, **never** `failed`. Not retried automatically; an operator decides |
| 12.3 | Store Syria is down for 20 minutes while events occur | the per-store feed loses them (no upstream retry); `lynomia:reconcile-events` and `lynomia:reconcile-consents` repair what they cover. **Record precisely what is NOT repaired** — that list is a Phase 7 deliverable |
| 12.4 | Skew one host's clock by 400 seconds | every delivery fails the 300-second signature window. Restore the clock and confirm recovery. This measures a real A1 unknown |
| 12.5 | Exhaust the per-store ingress rate limit with signed traffic | 429s; confirm an **unsigned** flood cannot consume a store's budget — the signature is checked before the per-store throttle precisely so an anonymous caller cannot destroy a merchant's deliveries |
| 12.6 | Set `LYNOMIA_INTEGRATION_ENABLED=false` and restart | no remote call is attempted by any surface or sweep. Restore |
| 12.7 | Kill the Store Syria worker mid-notice | the row is left `sending`; the console's in-flight tile shows it; nothing retries it automatically |
| 12.8 | Post a 300 KiB body to each ingress | 413 before the body is parsed |

## 14. Deployment, rollback and observability

### 14.1 Deployment order

Both sides ship from the same branch name but they are two deploys, and the order matters.

1. **Lynomia first.** It is the producer and the API. Its new surfaces (`message_delivery_status`
   in `ALLOWED_WEBHOOK_EVENTS`, `Delivery::StatusFeed`, `Partner::EventFan`) are additive: an
   older Store Syria simply never subscribes, and nothing it already relies on changes.
2. Run Lynomia's migrations, restart web and Sidekiq.
3. **Store Syria second.** Deploy with `LYNOMIA_INTEGRATION_ENABLED=false`.
4. Run Store Syria's migrations. The two new ones are additive: `lynomia_platform_events` is a
   new table, and the notices table gains five nullable columns and two indexes.
5. Restart web, worker and scheduler.
6. Turn the kill switch on.
7. Run `php artisan lynomia:reconcile-deliveries` once by hand, to register the subscription
   and see its output rather than waiting fifteen minutes to discover it failed.

**The reverse order breaks nothing but wastes the window**: Store Syria would register a
subscription for an event Lynomia's `Webhook` model does not yet allow, and the create would
be refused.

### 14.2 Rollback

| Situation | Action |
|---|---|
| Anything in §3–§13 fails in a way that is not understood | `LYNOMIA_INTEGRATION_ENABLED=false` and restart. This is the lever, and it is instant: no surface and no sweep performs a remote call while it is off |
| A Store Syria defect | redeploy the previous revision. The two migrations are additive and their `down()` is written, but **do not roll them back** to recover from an application bug: the columns are harmless when unread, and dropping them loses the outcome history |
| A Lynomia defect | redeploy the previous revision. Removing `message_delivery_status` from `ALLOWED_WEBHOOK_EVENTS` leaves existing webhook rows carrying a subscription the validator no longer accepts; those rows are not re-validated on read, so the feed simply stops. Acceptable for a rollback, and the subscription is re-created by the sweep on the way back |
| Data suspected wrong | nothing in this integration deletes merchant data. `lynomia_platform_events` is append-only and is the record of what was reported; read it before changing anything |

### 14.3 Observability — what to watch, and where

| Signal | Where | What a bad value means |
|---|---|---|
| Notices awaiting an outcome | Super Admin → notices tab | growing with no delivery reports = the feed is not arriving |
| Delivery reports received today | same | zero with notices outstanding = the subscription is gone |
| `lynomia_platform_events.skip_reason` distribution | database | a lot of `stale` is ordinary; a lot of `no_matching_notice` means the workspace is being used for something else; any `unknown_outcome` means the producer has a word this side does not know, which is a contract break |
| Indeterminate notices | notices tab | each one is a human decision about whether a merchant was told |
| Consent decisions pending / stuck / expired | consent panel | `expired` is the set an operator can act on |
| Commerce outbox depth | commerce panel | a backlog that does not drain |
| Open operations signals | partner console | |
| `lynomia:*` command output | scheduler log | a sweep that reports `unreachable` every run |
| 401/413/429 counts on both ingress routes | web logs | 401s mean a signature or clock problem; 429s on the platform route mean one global bucket is too small |

1. A latency table: consent withdrawal end-to-end, delivery feed per transition, commerce
   event to agent panel.
2. The §12.3 list of what a 20-minute outage does **not** repair.
3. The §13.2.5 number: the per-message cost of the new hook.
4. A defect list, each item classified as blocking, pre-production, or recorded.
5. A signed-off copy of this document with every GO/NO-GO marked.
