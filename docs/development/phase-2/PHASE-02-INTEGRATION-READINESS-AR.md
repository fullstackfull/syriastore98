## ٤. البند ١ — انحدار حالة HTTP: ما كان، وما صار

### الخلل

الشرط الأصلي في مواضع النداء الثلاثة كان:

```php
$response->successful() && ($result['status'] ?? null) == 200
```

أي **2xx على مستوى HTTP** *و* حقل `status` الخاص بالمزوّد. و`SafeWebhook::send()` يعيد الجسم
وحده، فمات رمز HTTP مع مقبض cURL — فحُفِظ الاختبار الثاني وسقط الأول. **وانقلبت حالة واحدة من
الفشل إلى النجاح: مزوّد يجيب بخطأ HTTP وجسمه يدّعي `status: 200`.**

وهذا ليس افتراضاً عن مزوّد معادٍ، بل شكل بوّابة معطوبة أو نصف منشورة. كان التاجر سيُبلَّغ أن
اختبار OTP أُرسل، و**المسار الموجَّه للعميل** كان سيطلب من المشتري انتظار رمز لم يخرج أصلاً.

وكنتُ قد أفصحتُ عن هذا الفرق في تعليق بالكود وأبقيتُه. **وكان قراراً خاطئاً**: التوجيه كان
باستخدام التنفيذ القائم لا بإعادة تقرير شرط نجاح، وتغيير السلوك المسجَّل في تعليق يبقى تغييراً
للسلوك.

### الإصلاح، وشكله

`SafeWebhook::sendWithStatus()` جديدة و**اختيارية**:

* **`send()` لم يتغيّر عقدها** — صارت إسقاطاً من سطر واحد لـ`sendWithStatus()` فلا تتباعدان، وتعيد
  الجسم أو `false` أو `null` كما كانت. ومتصلها الوحيد الآخر في التطبيق هو
  `Utility::WebhookCall` (`Utility.php:2119`) — مقيس — و`WebhookController` يستخدم `allows()` فقط.
  **ولا يرى أيٌّ منهما أي فرق**، و`WebhookSafetyTest` يمرّ دون تعديل.
* **`plan()` واحدة، فحماية واحدة** — نفس حكم `SafeRemoteFetch::check`، ونفس تثبيت
  `CURLOPT_RESOLVE`، ونفس `CURLOPT_FOLLOWLOCATION => false`، ونفس حدود البروتوكول والمهلة. الفرق
  الوحيد بين الدالتين هو **مقدار** الجواب المُعاد، وهذا ما يمنع صيرورتها مساراً ثانياً أرخص.
* **`CURLINFO_RESPONSE_CODE` بقيمة 0 يُبلَّغ كـ`null`** لا كحالة: «لا جواب» ليس رمز حالة.
* **مفصل الاختبار اكتسب شكلاً إضافياً** `['body' => ..., 'status' => ...]`، يُعرَف بوجود مفتاح
  `body` لا بكونه مصفوفة — فلا يُقرأ مفصل قائم يعيد مصفوفة كأنه تقرير حالة. وكل المفاصل القائمة
  تعيد نصّاً أو `false` (مقيس في ثلاثة ملفات)، فلم يتغيّر سلوك أيٍّ منها.

و`OtpTransport::succeeded()` هي الشرط المستعاد، في **مكان واحد** بدل نسخه في كل فرع — فالنسخة
السابقة كتبته مرّتين في متحكّمَين، وهكذا يُحدَّث أحدهما وحده يوماً ما:

```
outcome === ANSWERED  &&  http_status ضمن 2xx  &&  provider status === 200
```

و`successful()` هي مدى 2xx كلّه لا `== 200`، فـ201/202/204 تنجح كما كانت. **وحالة HTTP المجهولة
تفشل مُغلقةً.**

### الأدلة

| ما يُؤكَّد | الحالات |
|---|---|
| الانحدار نفسه — HTTP 500 مع جسم يدّعي `status: 200` | ١، بالاسم |
| لا شيء خارج 2xx يُعدّ إرسالاً | 400 401 403 404 429 500 502 504 و**302** (إعادة التوجيه لا تُتبَع، فتصل كما هي) |
| و2xx المشروع يبقى نجاحاً | 200 201 202 204 299 |
| 2xx مع فشل من المزوّد ليس نجاحاً — ورسالة المزوّد تبقى تصل إلى التاجر المُصادَق والمُصرَّح له | ١ |
| حالة HTTP مجهولة تفشل مُغلقةً | ١ |
| عقد `send()`: الجسم / `false` / `null`، ولا شيء يُرسَل عند الرفض | ١ |
| مصفوفة بلا مفتاح `body` هي جسم لا بيانات وصفية | ١ |
| `succeeded()` مباشرةً على جدول القرار كامل | ١٤ صفّاً |
| **مسار واتساب التجاري** — مثبّت على نقطته الخاصة، يرفض إعادة التوجيه، يرفض العنوان الداخلي، ويرفض خطأ HTTP المدّعي النجاح | ٣ |

**مسار واتساب لم يكن له أي اختبار قبل هذه الجولة.** قياس أوّلي:
`grep -rn "otp_channel.*whatsapp" tests/Feature/Security/` لا يجد شيئاً في أي من ملفي OTP — مع أن
لذلك الفرع نداءه الخاص لـ`OtpTransport::post()`، ومساره الخاص، ومصفوفة حقوله، وسجلّ رفضه، ونسخته
من شرط النجاح. **توجيه المالك باختبار «كلا مساري OTP التجاريين» هو ما كشفه.**

### الطفرات — كلٌّ أُعيدت بايتاً ببايت

| الطفرة | النتيجة |
|---|---|
| إسقاط شقّ HTTP مرة أخرى (الانحدار الأصلي) | **١٨ تفشل** |
| تضييق 2xx إلى 200 بالضبط (الإفراط في التصحيح) | **٤ تفشل** |
| إسقاط شقّ المزوّد (الانحدار المعاكس) | **١ تفشل** |
| اعتبار 0 حالة ناجحة | **١ تفشل**، وهي بالضبط ذلك الصفّ |
| شرط واتساب يُعاد إلى الشقّ الواحد | **١ تفشل**، بالاسم |
| إرسال واتساب يُوجَّه إلى نقطة SMS | **١ تفشل**، بالاسم |
| `SafeWebhook` يُبلّغ 0 كحالة لا كـ`null` | **مرّت بصمت** — انظر أدناه |

### فرعٌ لا تغطّيه المجموعة، مُعلَناً لا مُضمَراً

تحويل `0 → null` يقع على **مسار cURL الحقيقي**، والمجموعة لا تنفّذه أبداً: كل اختبار يمرّ عبر
المفصل. طفّرتُه ليمرّ 0 كما هو، **وبقيت المجموعة خضراء كلّها**. وما يُؤكَّد فعلاً هو الخصيصة التي
تجعل التحويل آمناً في الحالين: `succeeded()` ترفض 0 وترفض `null`، مُثبَّتاً بجدول القرار. فالتحويل
دفاعٌ في العمق للسجل ولأي مقارنة مدى مستقبلية، لا ما يستند إليه قرار النجاح. **وقول ذلك أصدق من
ترك مجموعة خضراء تُوحي بتغطية لا تملكها.**

3. **New ruleset** → **New branch ruleset**.
4. **Name**: مثلاً `main: PR + CI required`.
5. **Enforcement status** → **Active**. *(و**Evaluate** يسجّل ما كان سيحدث دون منع شيء — تقرير، لا
   حماية. لا تتركه عليه وتحسب `main` محمياً.)*
6. تحت **"Target branches"** → **Add a target** → **Include default branch**.
7. تحت **"Bypass list"** — **اتركها فارغة.** كل من يُدرَج فيها يتجاوز كل قاعدة أدناه. ومالكو
   المنظمة ومديرو المستودع **لا** يتجاوزون `ruleset` إلا إن أُدرجوا — وهذه ميزتها العملية الكبرى
   على المسار التقليدي.
8. تحت **"Rules"** علّم:
   * **Require a pull request before merging**
     * **Required approvals: 0** اليوم، و**1** في نفس جلسة فصل الهوية (§٧ — السبب أن GitHub يرفض
       أن يوافق الكاتب على طلبه، والأتمتة تفتح كل طلب بهويتك).
     * **Dismiss stale pull request approvals when new commits are pushed** — مُفعَّل.
   * **Require status checks to pass**
     * **Require branches to be up to date before merging** — مُفعَّل.
     * **Add checks** → أضف الأسماء الستة في §٢ **حرفياً** واحداً واحداً.
   * **Block force pushes** — مُفعَّل.
9. **Create**.

### المسار (ب) — حماية الفرع التقليدية

1. **Settings** → الشريط الجانبي → **Branches**.
2. تحت **"Branch protection rules"** → **Add classic branch protection rule**.
3. **"Branch name pattern"**: `main`.
4. **Require a pull request before merging**
   * **Require approvals** → **0** اليوم، **1** عند فصل الهوية.
   * **Dismiss stale pull request approvals when new commits are pushed** — مُفعَّل.
5. **Require status checks to pass before merging**
   * **Require branches to be up to date before merging** — مُفعَّل.
   * في صندوق البحث أضف الأسماء الستة حرفياً.
6. **Do not allow bypassing the above settings** — **وهذه هي المهمّة.** بدونها يكون مدير المستودع
   — وهي الهوية التي تستخدمها الأتمتة الآن — مُعفى من كل مربّع أعلاه، فتكون الحماية استشارية
   تحديداً تجاه الفاعل الذي وُضعت لتقييده.
7. **Create** ثم **Save changes**.

### تحذير واحد مُقيس

**لا تُضف `Security-sensitive diff: human approval` إلى الفحوص المطلوبة بعد.** إنه في وضع
`report`، وسطر استخدامه نفسه يقول «الخروج ٠ = وجود موافقة مؤهّلة، **أو** وضع `report`». ومقيس على
رأس #126: **`success` على طلب دمج بصفر مراجعات.** فاشتراطه اليوم يضيف اسماً يبدو كاشتراط مراجعة
بشرية **ولا يُقيّد شيئاً** — وهو أخطر من بوابة غير قابلة للاستيفاء، لأن تلك تُعلن عن نفسها أول
محاولة دمج.

**وكل ما سوى ذلك في الخطوة أعلاه قابل للتطبيق اليوم**، ويستغرق نحو أربع دقائق، وهو أعلى تغيير
قيمةً متاح الآن: فهو يحوّل كل بوابة في هذا المستودع من **تقرير** إلى **قيد**.

## ٧. فصل الهويات (البند ٤، تكملة)

**الأتمتة تعمل بهوية كاتب طلبات الدمج نفسها.** مقيس: `gh api user` → `fullstackfull`، والطلبات
#125 و#126 و#127 و#128 كلها `author: fullstackfull`. وGitHub **يرفض** أن يوافق كاتب الطلب على
طلبه، فشرط «موافقة من هوية غير الكاتب» **غير قابل للاستيفاء اليوم مهما فعلتَ**.

**الموصى به: تطبيق GitHub** باسم مثل `storesyria-claude-code`:

* **Settings** → **Developer settings** → **GitHub Apps** → **New GitHub App**.
* صلاحيات المستودع: `Contents` (قراءة/كتابة)، `Pull requests` (قراءة/كتابة)، `Metadata` (قراءة)،
  `Actions` (قراءة)، و`Issues` فقط إن أردتَ أن تُسجّل الأتمتة النتائج.
* **ولا تمنح `Administration` إطلاقاً** — فهي الصلاحية التي كانت ستتيح للأتمتة تعديل الحماية التي
  تُنشئها أنت، وحجبُها هو ما يجعل «المالك يحتفظ بالسيطرة» واقعاً لا وعداً.
* ثبّته على `fullstackfull/syriastore98` **وحده** (*Only select repositories*).
* ثم: **أنت وحدك** من يستطيع تقديم موافقة مُستوفية، **وأنت وحدك** من يستطيع تغيير الحماية.

**وبعد الفصل فقط**: ارفع `Required approvals` إلى 1، وبدّل `report` إلى `enforce` في
`security-attestation.yml`، ثم أضف فحص الموافقة إلى الفحوص المطلوبة — في طلب دمج مُراجَع، وتحقّق
عليه أن الفحص **أحمر دون موافقة وأخضر معها**؛ فتبديلٌ لا يُرى تغيّر حالته ليس مُثبَتاً أنه يعمل.
