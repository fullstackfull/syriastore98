## What this domain is

Three separate mechanisms sit under one heading and they do not know about each other. (1) The ORDER REFUND workflow — `order_refunds`, requested by the shopper on the storefront and actioned by the merchant through five AJAX mutators in `OrderRefundController` — is among the best-hardened commerce surfaces in this repo: an explicit state machine with terminal states, a server-side amount cap, per-refund restock idempotency behind a cache lock plus a durable `order_notes` marker, a per-line `refunded_qty` clamp, and roughly 120 existing test methods across seven files. (2) The ORDER RETURN workflow — `Order::product_return()`, reached from the merchant web door and from `POST api/{slug}/product-return` — is a different code path with its own markers. (3) The CANCELLATION workflow — `OrderController::status_cancel` — is a third. The single most important thing to know is that the refund door sits OUTSIDE the cross-door stock protocol the other two share: `OrderRefundController` contains zero references to `Order::LINE_STOCK_RESTORED` and never calls `StockMovement::movedOutFor()`, although that constant's own docblock (app/Models/Order.php:886-889) asserts "a refund or return reads it as evidence". A line returned through `product_return` can then be refunded and restocked a second time. Separately, `Order::product_return()` recomputes the order total from the already-reduced `final_price` while summing every returned line, so returning a second distinct line over-subtracts and can drive `orders.final_price` negative. No refund path anywhere calls a gateway refund API: `RefundIntegrityService::hasGatewayRefundDriver()` is hardcoded false, and the two refund clients that do exist in `app/Libraries/` (Easebuzz `refundAPI`, PhonePe `initiateRefund`) have no caller in app/, packages/ or routes/. The shipped Flutter merchant app has no refund surface at all.
