## What this domain is

Payment core here is heavily and genuinely hardened, and most of what a naive audit would flag is already closed and pinned by tests. The storefront trust boundary is real: seven gateway-return handlers read ONLY the server-stored checkout state, pin customer_id and method_id against a bare merge, take a two-key replay claim built on a server-minted checkout nonce, refuse foreign products and variants and absurd quantities, and derive payment_status through PaymentVerificationService rather than asserting the literal 'Paid' - so no unverified gateway payment is recorded Paid anywhere. THE SINGLE MOST IMPORTANT THING A READER MUST KNOW is that all of this protects the SUCCESS leg: the CANCEL and DECLINE legs of Stripe, PayPal, Sofort and Paymera point at the same order-writing route as success, the return_type marker meant to distinguish them is written at 11 sites in app/ and read at none, and no test in the repository drives a cancel URL - so cancelling a payment still creates an order and decrements stock. Verification coverage is narrow and asymmetric: only four of ~52 payment types have any server-side capture producer (AuthorizeNet and NMI, which make the charge themselves; Khalti's verify call, now bound to the server's figure; Paymera's poll plus amount plus signature), only three are amount-enforced, and Paymera is double-gated shut today by a hardcoded test gateway host and a signature scheme that is unconfigured and required by default. Exactly one storefront path has an inbound signature check of any kind (Paymera's), and Paymera's server-to-server trigger sits behind auth so the gateway can never reach it - meaning no storefront payment in this platform has a working webhook confirmation channel. The durable idempotency record (order_gateway_references) exists, is fully tested, and has zero production writers by design, so all gateway-return idempotency currently lives in the cache.
