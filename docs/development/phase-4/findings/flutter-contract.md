## What this domain is

The shipped Flutter admin app calls 84 live endpoints under https://storesyria.com/api/admin (8 more are commented out in lib/utils/base_api.dart). I ran the repo's own cross-repo gate — `php tests/Support/ApiContract/bin/check-contract.php --app-repo=/home/user/StoreSyria_app98` — and every one of the 84 resolves to a registered route (0 unresolved, 219 server routes parsed), so the *structural* contract is intact and is wired into CI at .github/workflows/ci.yml:412. The single most important thing to know is that the TENANT boundary on this surface is thorough and well-tested, while the INTRA-TENANT permission boundary is not: `resolveOwnedStore()` guards essentially every handler, but only 8 of them carry a permission gate. P2-07-13 gated the five list endpoints that serve money (`orderlist`, `Top_orders`, `productlist`, `couponlist`, `staticsdata`) and left their siblings — `vieworder`, `deleteorder`, `assignOrders`, `searchdata`, `searchproduct`, `searchProductsByName`, `customerlist`, `customer/orders`, the order-note pair and the whole DeliveryBoyApiController — serving or writing the same data with no permission check, while each one's web twin requires a named Laratrust permission. Second, `POST /api/admin/orders/update-status` is a *second, independent* order-status writer that does not go through `Order::order_status_change()`: it has no transition guard, it writes `return_status = 2` where the web writes 1, and it omits the `payment_status = 'Unpaid'` that makes cancellation reach the financial observer. Third, the 401-forces-logout hazard is real and already live on one path the app calls (`POST /api/admin/update-customer`), recorded and pinned as a known gap rather than fixed.

### P4-F105 — CONFIRMED — HIGH

**CONFIRMED: /api/admin/orders/update-status writes delivered_status with no transition guard, and its Return arm stamps return_status=2 without restocking, which silently disarms the web's restock-on-approval guard**


**Corrected statement (reviewer):** Two corrections, both of which widen rather than narrow the claim. (a) **The web's guards are not the ones described.** Cancel is refused when `delivered_status != 0` (Order.php:702), i.e. from *any* non-pending state — so the API gap is wider than "a DELIVERED order can be cancelled": Confirmed, Picked Up, Shipped and already-Returned orders can all be cancelled over the API. Return is refused only when `delivered_status == 0` (`:757`), so the web already permits Return from Shipped/Picked Up/Confirmed; the API-only gap on that arm is specifically **Pending → Return**, not "never-delivered → Return". (b) **The consequence is not confined to a wrong status value.** The API's Return arm writes `return_status = 2` with no restock (DashboardController.php:559), and that is the exact value `OrderController::order_return_request` uses as its durable restock idempotency marker (OrderController.php:1421-1422). An app-side "Return" therefore disarms the merchant's subsequent genuine web approval: `restoreReturnedStock()` is skipped, the response still reads "Return request approve successfully", and the returned stock is lost permanently and silently. The Cancel arm's omission of `payment_status = 'Unpaid'` likewise leaves `OrderObserver` (which fires only on a `payment_status` change) from ever reversing the wallet credit on a cancelled order. Severity classification: this is a commerce-correctness/data-integrity defect, **not** a security finding. `sameStore` holds (OrderPolicy.php:38-48) and the gate requires `Manage Order`, so the actor is a merchant or their own staff acting on their own tenant's orders, with no privilege gain and no cross-tenant reach. "High" still stands, but it rests on the silent permanent inventory loss reachable through the shipped app's ordinary two-tap status sheet, not on the transition itself.
