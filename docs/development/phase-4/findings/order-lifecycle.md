## What this domain is

There is no order state machine. `Order::order_status_change()` (app/Models/Order.php:695-845) is a flat chain of `if ($order_status == '...')` arms and only two of them test the order's current state: `cancel` requires `delivered_status == 0` (:702) and `return` requires `delivered_status != 0` (:757). The `confirmed`, `pickedup`, `shipped` and `delivered` arms set a date, save and return `success` unconditionally, so any status can follow any other — a Cancelled order can be moved to Delivered, and the merchant order board offers exactly that in two clicks. Six independent doors write `delivered_status` (merchant web, merchant board, Flutter `orders/update-status`, `api/admin/status-change`, the two API `order-cancel`s, the storefront customer API, and the Delivery Syria webhook, which bypasses the shared writer entirely), and they disagree about restock, payment reversal, notification and the order-note trail: only ONE of the five cancellation doors restores stock, and it is the one the storefront never renders a button for. Authorization and tenancy on these paths are genuinely well hardened — `OrderPolicy::updateStatus` is operator-first, the route id is pinned to the URL segment, `OrderDocumentAccessGuard` covers every order read, and a large body of tests (OrderStatusChangeOwnershipTest, StorefrontOrderMutationAuthorizationTest, DeliveryAndOrderApiAuthorizationTest, AdminApiOrderWritePermissionTest, OrderCancelRestockTest, ReturnApprovalStockTest, OrderReplacementTest) pins it. What is untested everywhere is *which* status each principal may set and *from* which status — the vocabulary and the ordering, not the identity of the caller. The single most important thing to know: the only code that gives a cancelled order's stock back lives in `OrderController::status_cancel()`, reachable only from a storefront control that no rendered view contains.
