## What this domain is

The cart is a database table (`carts`, one row per product+variant line) with two completely separate code paths that must agree: a GUEST path keyed on a `cart` cookie (`Cart::cart_list_cookie()`, `Cart::cart_qty_cookie()`, the guest arm of `CartController::product_cartlist()`) and a SIGNED-IN path keyed on `customer_id` (`Api\ApiController::cart_list()`, `addtocart()`, `cart_qty()`). The single most important thing to know is that `carts.price` is written by five code paths and READ BY NONE — both readers re-derive every line price from `Product::ProductPrice()` or the `product_variants` row — so a caller cannot move the price by poisoning the cart row, and the S16/S19 request-input and cross-tenant-product families have already been closed here with tests. What is NOT closed is the cart's COUPON ARITHMETIC: `Cart::getCouponTotalAmount()` is invoked once per cart LINE, so a `flat` coupon subtracts its full amount from every line, while `apply_coupon()` subtracts it once from the basket — and the cart's `total_sub_price` is what `PaymentService::getProductStatus()` writes into `orders.final_price` for COD. Beyond that the domain's defects are seams rather than holes: the guest basket is written under `session()->getId()` but read from a 24-hour cookie whose lifetime is 12x the session's; the web cart writers never check that the signed-in customer belongs to the store in the URL although their API twins do; `cart-check-guest` is the one cart endpoint with no principal check and no store predicate at all; and several handlers 500 where their immediate siblings return a clean refusal. Roughly half of `cart_list_cookie()` is module branches (WholesaleProduct / SizeGuideline / ProductPricing) that no test run reaches, and `SizeGuideline` is not even among the 70 vendored modules, so those branches are dead on this installation.

The NULL-`tax_id` variant (Laravel rewrites `where($col, null)` to `whereNull`, Builder.php:870-871) is likewise unreachable because the sole writer always sets a non-null `tax_id`. The disclosure needs a legacy or imported `tax_methods` row with a NULL or cross-store `tax_id` — possible on production data, not creatable by the code. 2. "with none of the null guards its siblings carry" is wrong, and inverted on the `$plan` half. `get_shipping_method` (:558-560, :590, :600) dereferences a possibly-null `$store` exactly as `get_tax_data` does, and `cart_list_sidebar:39-40` does `Plan::find(User::find($store->created_by)->plan_id)` with no `$user` check at all — weaker than `get_tax_data`'s `if ($user)` at :992-994. Only the `$store` guard is a genuine sibling-vs-this gap, and only against `cart_list_sidebar:31-37`. What actually survives: an unconditional cross-tenant read of one low-value column — the foreign product's `tax_id`, echoed as `tax_id_value` in both branches (:1057 and :1105→:1112, the guest path ungated by `count($taxs)`) — plus an existence oracle and a latent tenant boundary on a pricing handler. Worth a one-line fix using the in-tree helper shape `ModuleStorefrontInputGuard::productOfStoreOrAbsent()`, classified as hardening rather than a price-disclosure vulnerability.

**The test it asks for:** `tests/Feature/Commerce/GetTaxDataResolvesProductInSlugStoreTest.php`. Two tenants, fixtures written through Eloquent — `Product` and `TaxMethod` are `Cachable`, so a `DB::table()` insert would leave Eloquent reads serving a stale row. Fixture: merchant A owns store A (slug `store-a`), merchant B owns store B. Both merchants' `plan_id` points at a `Plan` whose `shipping_method != 'on'` (the `$plan->shipping_method` read at :1036/:1108 is unguarded, so a null `$plan` is a 500 that would make the test pass for the wrong reason). Store B gets a `Tax` row and a product whose `tax_id` is that tax's id — a value store A can never own, given `TaxMethodController::store()`'s invariant. Assertion 1 — the cross-tenant read that is live today, no auth needed (guest branch). `POST /store-a/get-tax-data` with `product_id = <store B's product id>`. Today the guest branch takes :1105 (`$tax_id = $Product->tax_id`) and the response carries `tax_id_value` equal to store B's tax id. Assert the response's `tax_id_value` is NOT store B's tax id — after the fix the foreign product resolves to null and :1103 echoes the caller's own posted `tax_id_value` (or null). Assertion 2 — positive control, or the test proves nothing. Same route, same store A, `product_id = <store A's own product>`: the response must still carry store A's product's `tax_id`. Without this, a fix that refuses every product satisfies assertion 1. Assertion 3 — the signed-in branch. Sign in a store-A `Customer` via the `customers` guard and repeat; `sale_price` must not equal store B's product's `sale_price`. Note this one passes today for the reason in the corrected claim (`count($taxs)` is 0), so it is a regression pin on the boundary, not a reproduction — label it as such in the test so a later reader does not mistake it for the failing case. Assertion 4 — the unknown-slug dereference. `POST /no-such-store/get-tax-data` must not return 5xx; today `$store->created_by` at :991 is a null dereference. Pair it with a real slug returning 200, the way `tests/Feature/Storefront/UnknownStoreSlugFailsClosedTest` pairs every unknown-slug case, since that test's provider covers only GET pages and not this POST route. Per this project's stricter TDD rule: after the fix, revert it and confirm assertions 1 and 4 fail again — assertion 1 in particular could pass for the wrong reason if the fixture's `$plan` is null and every request 500s.
