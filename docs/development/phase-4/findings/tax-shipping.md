## What this domain is

Tax and shipping in this codebase are two separate engines joined only at checkout. Tax rules live in `tax_methods` rows (rate + optional country/state/city + a string `priority`) grouped under a `taxes` row, with store-wide switches in `tax_options`; shipping lives in `shipping_zones` (country+state) each owning `shipping_methods` rows (`Flat Rate`, `Free shipping`, `Local pickup`, and this fork's custom `Delivery Syria`), with per-product `shippings` classes buckets. The cross-tenant layer is in good shape and has been hardened repeatedly: F258/F261/F263 scoped every merchant-side CRUD handler, P01-COMMERCE-SEC-01 scoped the `method_id` lookup at both checkout legs and floored a negative shipping charge, F283 threaded the store through both flat-rate calculators, and `OrderTaxResolver` means no client-supplied `tax_price` can reach a charged total. **The remaining weakness is not tenancy, it is the tax engine's own correctness.** `Cart::getProductTaxAmount()` has a fallback branch that charges a tax method whose country/state/city do NOT match the shopper whenever the store's `price_type` option is set to anything but `inclusive` — so for an exclusive-priced store the jurisdiction columns are inert — and the catalogue price (`Tax::tax_methods()`, top-`priority` band only) and the cart (`Cart::getProductTaxAmount()`, every method summed) compute tax from different sets of rows. Separately, `Api\ApiController::place_order` reads its tax from `$cartlist['tax_info']`, a key `cart_list()` never produces, so the API order writer records zero tax for any store whose plan has the shipping engine off.
