Part of `../PHASE-04-FINDINGS-REGISTER.md`. Inventory by one agent; every claim below then

## What this domain is

This domain has already absorbed several dedicated security passes (S16, S19, P01-SEC-11/12/14, P1-ORD-07/10/12, P25) and the authorization story is now genuinely strong: `ApiController::resolveStoreCustomer()` is the single predicate behind every storefront-API customer handler, `AccountProfileController` has its own four-helper family (`shopper`/`ownedAddress`/`ownedTicket`/`ownedOrder`) pinned by a comment-stripping census test, and `OrderDocumentAccessGuard` covers the three order-document URIs the account pages use. I found NO surviving instance of the headline `if (! auth('customers')->user()) { $id = $request->some_id; }` trap on any commerce path — every one of the sites CLAUDE.md names has been rewritten to derive the principal from the guard, and merchant/driver-token negative cases are driven by name in the Security suite. The single most important thing a reader must know is that the remaining defects in this domain are NOT authorization holes — they are **wiring defects on the account-creation and address-book journeys that no test touches**: the storefront checkout's "Create an account?" checkbox can never submit the value its handler tests for, the account that path would create gets its password-reset link minted on the wrong password broker (the `users` broker, against `App\Models\User`), and the address form collects two fields (`address_type`, `instructions`) whose names match neither the model's `$fillable` nor the table. Two unscoped `DeliveryAddress::find($request->billing_address_id)` reads also survive in `CartController` and `ApiController`, outside the reach of the bare-id census test, which only greps `AccountProfileController`.

## Covered by existing tests

- A merchant's or a driver's Sanctum token cannot read or write any shopper's profile, addresses, wishlist, order history, returns or reward points through the storefront API — the guard-class trap, driven with all three token classes rather than only a customer token — ``
- Address create, update, delete and the `main`-address write refuse a merchant token, a driver token, another shopper and a shopper of another store, and a posted `customer_id` is ignored; setting a default demotes only the caller's own rows — ``
- The storefront web account area: no address or ticket handler resolves a row by a bare id, a merchant or driver SESSION cannot reach a shopper's address or ticket, and a shopper's own legacy rows with a NULL store still work — ``
- Which customer-account routes are gated and which are deliberately anonymous, asserted in BOTH directions so a future 'fix' cannot break storefront signup or the checkout location lookups — ``
- Account self-deletion deletes only the caller, never a `users` row, never another customer who happens to share the integer, and preserves the merchant's order history — ``
- Order documents reached from the account pages (`{storeSlug?}/order/{id}`, `{storeSlug?}/customerorder/{id}`, `{storeSlug?}/order-refund/{id}`) are authorized at middleware level, with the raw and the Crypt-encrypted id forms both refused for a non-owner — ``
- A customers-broker reset token cannot reset a `users` row and vice versa; a reset requested through one storefront resolves that store's customer; a token issued for one storefront is not accepted through another — ``
- The customer OTP recovery flow: replay, expiry, attempt limits, cross-store slugs, and that an administrator's, operator's or driver's token cannot authorise a customer password change — ``
- Guest checkout's `customers` lookup is store-scoped, so a guest checkout in store B cannot write to or be attributed to store A's customer — ``
- Checkout's delivery-address write lands on the account being created, demotes only that account's own previous default, and the API handler it used to call still refuses an anonymous caller — ``
- The same address registered in several stores recovers independently — the reset key is the account id, a token minted for one store's customer is invalid for the others, and an archived account cannot be resolved for recovery — ``
- `(email, store_id)` uniqueness is the owner-approved policy and the merchant web form and the two Flutter admin writers now agree on it; the database constraint is explicitly NOT authorised and there is no unique index on `customers.email` in production — ``
