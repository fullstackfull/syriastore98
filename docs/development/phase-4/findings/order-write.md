## What this domain is

Order creation happens at sixteen or more write sites across five surfaces, and the hardening is real but unevenly distributed: the three writers named in OrderWriteTransactionTest are transaction-wrapped with stock compensation, five writers have double-submit claims added one at a time (F95, F226, F269, F276), seven gateway returns claim through GuardsGatewayReturn, and the merchant-web and Flutter-admin writers both carry store-scoped product and variant predicates with atomic decrements. The single most important thing to know is that the completeness machinery stops at a directory boundary: Tests\Support\Commerce\OrderWriteCensus roots at app/Http/Controllers, so GatewayReplayGuardCensusTest's assertion that it classifies "EVERY customer-order write site" silently excludes App\Services\PaymentService::getProductStatus — the writer that actually runs for cash on delivery, the ordinary Syrian checkout — and the LotteryPrizes module writer. That writer is the one live order path with no duplicate-submission control of any kind. Totals are recomputed server-side everywhere and no posted money field reaches a persisted total, but the recomputation itself is wrong on two branches of ApiController::ordersave: with the plan's shipping on it stores the delivery charge alone as final_price, and the plan that decides this is resolved from Cache::remember('admin_details') — the lowest-id admin row in the shared database, i.e. another merchant — while the same method resolves the store owner's plan forty lines earlier for the quote. Order identifiers are known not to be identifiers and are mitigated only for the thank-you page; ordersave additionally discards the authenticated form of the number one line after computing it. Finally, the merchant-web writer is missing the customer-ownership predicate its own Flutter twin added, and three writers key product_json lines "quantity" where the P&L service and the return workflow read "qty".
