## What this domain is

Stock arithmetic on this platform is already hardened and funnelled through one primitive: every `decrement()`/`increment()` on `products.product_stock` and `product_variants.stock` in `app/` lives inside `App\Services\ProductStockService`, which issues a single conditional UPDATE (`SET col = col - ? WHERE id = ? AND col >= ?`) so concurrent checkouts cannot lose an update, and a real-MariaDB harness (`tests/Support/Security/bin/verify-stock-oversell-concurrency-on-mysql.php`) proves it. The DECREMENT side is in good shape: the web checkout pre-flights the whole cart before any destructive write, every one of the seven gateway writers gives its decrements back on an in-loop exit and on a failed order write, and both merchant-admin order writers use the atomic conditional UPDATE with an availability predicate. The RESTORE side is where the holes are, and they cluster on one question: who is allowed to say "this order is cancelled / returned" and who actually puts the goods back. Only ONE of the five cancellation doors restores stock — the storefront web `POST {storeSlug}/status-cancel` — so a merchant cancelling in the admin, a customer cancelling over the storefront API, the Flutter admin app and the Delivery Syria courier webhook all leave the inventory consumed for good. The courier webhook is the worst of these because it writes `return_status = 2` directly, which then permanently disarms the merchant's own return-approval restock through its `$previousReturnStatus !== 2` idempotency guard. Separately, the return-approval restock never consults the stock-movement record (only the cancellation door does), so a store with `stock_management = 'off'` — the shipped default — gains inventory it never spent.
