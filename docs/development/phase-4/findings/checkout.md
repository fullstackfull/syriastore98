# Phase 04 findings — checkout

Part of `../PHASE-04-FINDINGS-REGISTER.md`. Inventory by one agent; every claim below then
handed to an independent reviewer told to refute it. `CONFIRMED` means the reviewer tried and
could not. The **corrected statement** is the reviewer's, and it supersedes the original claim

## What this domain is

The storefront web checkout is a thin page (HomeController::checkout:1180-1187 only renders a view) whose real work happens in four AJAX endpoints on CartController/OrderController and in one very large handler, PaymentController::processOrder (app/Http/Controllers/PaymentController.php:1841-2016), which assembles the order and hands off to PaymentService::process. The money-assembly half of that handler has been hardened repeatedly and well: the caller's shipping_final_price is zeroed, tax is derived by OrderTaxResolver, the coupon is re-validated server-side with final_sub_total pinned, the basket is pre-flighted for foreign products, non-positive quantities and stock, and the PartialPayments balance is read from the stored row rather than the request. The single most important thing a reader must know is that the money assembly is NOT finished where it looks finished: for `cod` and `bank_transfer` the order is written by App\Services\PaymentService::getProductStatus, and that writer decides whether a shipping charge exists at all from `Cache::remember('admin_details')` — the lowest-id `type = admin` user on the whole platform — not from `$store->created_by`, so one unrelated merchant's plan sets another merchant's COD totals (PaymentService.php:2260-2265, :2484, :2806-2810). That writer also lives in app/Services/, which the project's own order-writer census (tests/Support/Commerce/OrderWriteCensus.php:64) cannot see, so its absence from the replay-guard buckets reads as coverage rather than as a blind spot. Beyond that, checkout's validation half is much weaker than its pricing half: an unknown slug, a failed billing validation and an absent optional billing key each produce a 500 rather than a refusal, nothing checks that the chosen payment method is actually enabled for the store, and the `place.order` route two security tests describe as "guest checkout submit" points at a controller method that does not exist.

## What already holds (12) — verified controls, do not "fix" these

- **A caller-supplied shipping_final_price cannot enter the cart read the order is priced from: processOrder zeroes it before getCartData, and the server's own delivery_price is merged back in by prepareFinalRequestData.**
  - `app/Http/Controllers/PaymentController.php:1894 ($request->merge(['shipping_final_price' => 0])), :2600-2606`
- **Tax charged at checkout is derived from the server's own cart and shipping computations, never from the posted tax_price; a negative figure resolves to 0.0 and a mismatching posted value is logged.**
  - `app/Services/OrderTaxResolver.php; app/Http/Controllers/PaymentController.php:2552-2586 (processShipping)`
- **The posted coupon_info short-circuit is gone: apply_coupon always runs server-side, final_sub_total is pinned to the server subtotal so a caller cannot inflate the discount base or walk past a minimum-spend gate, and a declined coupon yields coupon_price 0 and an empty coupon_info instead of a 500.**
  - `app/Http/Controllers/PaymentController.php:2422-2545 (processCoupon)`
- **A read-only whole-cart stock pre-flight runs before any gateway hand-off and before any destructive loop, and refuses an unfulfillable cart without writing anything.**
  - `app/Http/Controllers/PaymentController.php:1911-1917 (assertCartAvailable call site)`
- **A basket naming another store's product, and a basket holding a non-positive line quantity, are both refused at the web checkout before payment initiation.**
  - `app/Http/Controllers/PaymentController.php:1919-1975 (basketHasForeignProduct and the nonPositiveLines refusal)`
- **A PartialPayments 'settle an outstanding balance' checkout reads the payable from the order_partial_payments row, and only if that row is this store's, this signed-in customer's and still awaiting payment; a gateway that cannot settle a balance is refused before the card is charged.**
  - `app/Http/Controllers/PaymentController.php:2654-2730 (prepareFinalRequestData pending_payment limb)`
- **The shipping method applied at checkout is store-scoped (or a null-store_id legacy row), and every shipping money branch is floored at zero so a merchant-authored negative cost cannot discount the goods.**
  - `app/Http/Controllers/CartController.php:560-588, :646-652`
- **A guest checkout's customer lookup is store-scoped, so a guest in store B cannot adopt or mutate store A's customer row; and a checkout-created account gets a 64-char random password rather than the committed literal.**
  - `app/Http/Controllers/PaymentController.php:2088-2092, :2135-2144`
- **The DeliveryAddress written during checkout registration resolves country/state/city through BillingGeography::resolveIds rather than writing posted names into foreign-key columns, and demotes other defaults scoped to that customer.**
  - `app/Http/Controllers/PaymentController.php:2175-2204 (addCustomerAddress)`
- **Cart rows are accumulated during the stock loop and deleted only after the order commits, so a part-way checkout failure no longer leaves a half-emptied cart with no order.**
  - `app/Services/PaymentService.php:2716-2722 (the deferred-clear comment) and the clearCartLines call after DB::commit()`
- **The storefront API checkout derives its subject from the session (resolveStoreCustomer) and ignores the posted customer_id, and it takes a fingerprinted intake claim immediately before the stock loop so a retried post does not write a second order.**
  - `app/Http/Controllers/Api/ApiController.php:3459-3463, :3698-3701`
- **POST {storeSlug}/process-order is NOT CSRF-exempt: the except list contains '*/checkout' (a read-only Route::any page) but no process-order entry.**
  - `bootstrap/app.php:403-456; app/Http/Controllers/HomeController.php:1180-1187 (the exempted route performs no write)`
