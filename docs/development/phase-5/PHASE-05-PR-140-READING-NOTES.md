# Reading notes for pull request #140 — what to know before reading the diff

These are the reviewer notes that lived in the pull request description until 2026-11-22. They were
moved here because the description reached GitHub's 65,536-character limit and had therefore been
**unable to record roughly 130 commits** — it still named `4324e4da` as the head while the branch
had moved far past it. A description that silently stops listing the branch's contents is the same
failure the deletion audits in `docs/security/` exist to prevent, so the fix was to move the
accumulated prose here and let the contents table keep growing.

Nothing is edited. Each note is reproduced verbatim, in the order it appeared.

Two notes stayed in the description because a reader must not miss them: the HIGH that is closed
for new rows only, and the fact that this repository is public and these findings already are.

* **P1-SEC-67c changes what three kinds of account see, and you have not decided it.** The settings helper now answers with no settings when the user's employer is not a merchant account. That reaches **a merchant who has changed their own `type`** (possible today), **their staff**, and **staff the operator created** (not creatable through `POST /users` on a database seeded from this repository — read, not executed; possible if the production operator's row carries a plan, or if legacy rows exist), and any user whose creator row is missing. Before, the first and third were served *the operator's* settings — a leak for the first; for the third, whether it was one is the delegation question you have not answered; the second were served their employer's own, and lose those too. Read from the code, not executed as requests: prices fall back to a `$` symbol; list avatars fall back to the placeholder; the vendored mailbox module sends mail without its attachment; the Settings tabs render blank, and saving a tab with no required field can write blanks over stored values while reporting success; for a store whose **owner** changed their own `type`, order and stock mail now returns a failure (I did not check whether each caller shows it). Executed in tests: the list behind the workspace chip is empty for all three, so the chip offers no store switch; `POST /user-unable` still answers 200, with empty counters, for the first two. **The main admin layout does not read this helper for these accounts, so its direction and theme colour are unchanged** (two published commits, `8c4556cc` and `f317e217`, say in the work queue that they were lost; `0be40da6` corrects it). `detect-D` lists the affected users and, by store ownership, which of them are merchants.

* **P1-SEC-67d costs operator-created staff the unlinks this rule decides, and leaves the storage counters open.** A signed-in panel user who is not an operator no longer gets the operator's upload-folder exemption by presenting the operator's id. A merchant who changed their own `type` keeps the store they own and loses every other store's folder — that was the hole. **Staff the operator created lose every unlink this rule decides under a store folder, the operator's own store included**: in first-party handlers a replaced image's old file stays, a product they delete keeps its media, and the storage figure charged for their uploads is not credited back; no handler turns the refusal into an error (the three sites that test the return were read). Staff of a self-demoted merchant are *not* affected: this rule is deliberately narrower than the family's. **Open, MEDIUM, and yours:** the storage counters still account against the id presented, so for the same two kinds of account uploads are charged to the operator's row. Two remedies were proposed and they differ — refuse the upload, or account it against the acting user's own row (my recommendation, by reading and not built: for a demoted merchant it restores the accounting that applied before the demotion, and unlike the first it adds no refusal). Six lesser items (LOW or informational) and two leads that have not been executed are in §k).

* **An owner fork I cannot decide for you.** A merchant can change their own `type` (a "supported action" per the P0 write-up, although the Users screen never lists a merchant's own account); that collapses their tenant root onto the platform operator. Every fix of this family applies one rule — *a tenant root that is not a merchant account confers nothing of the root's* — and leaves the operator as before: the ten sinks refuse, the global scope narrows to the user's `current_store`, the settings reader, the chip and the toggle's counters answer empty, and the settings writer still accepts the save but leaves the writer's own id on it. `RolePolicy` documents **operator-created staff** as a designed population, and they cannot be told from such a merchant by their root. So the cost falls on three kinds of account (second bullet). **Choose:** (a) keep the rule — what is built; (b) close the *enabling step* (a small change) **instead of** the rule. (b) stops NEW demotions only: relaxing the rule is safe only once no already-demoted merchant remains, because for one who is, every relaxed check reopens. The settings writer's rule should stay either way. Or both: new demotions stop, and the cost stays for everyone it falls on today.

* **The scope and settings fixes are not retroactive: neither changes a row that already exists.** Access to the operator's store that a user already holds through a stale `current_store` is not revoked by the scope fix, and the affected set can still grow until the pointers are re-pointed. Settings rows already stamped with the operator's id are not repaired either (first bullet). The queries for both are in the work queue (§f, §i), which also says what they cannot return; what to do about them is yours.
