# Dependency-Advisory Review Register — Store Syria

**Scope:** 66 advisories across 22 installed packages, reviewed per-advisory for reachability in this codebase. Every review was read-only: no project file was modified, no `composer` write command was run, and only `composer show --all` / `composer audit --locked` were executed. Four findings were put through an adversarial second pass; four of those passes found a path the first reviewer missed and are treated as the correct verdict below.

**Directive compliance:** this register recommends **no increase to `AUDIT_CEILING`** (deliberately lowered 70 → 58) and **no weakening of any check**. Where an upgrade clears advisories, the register says to *lower* the ratchet in the same change, because the gate asserts the count in both directions.

---

## 1. Bottom line

Of the 66 advisories, **27 are genuinely reachable, 34 are not reachable, 4 are undetermined, and 1 (the fifth `laravel/framework` entry) is not individually dispositioned in the evidence** — it shares the same four version constraints as the other four, so `v12.69.0` clears it regardless. Of the 27 reachable, 24 are driveable by a real application principal today; the other three are qualified: `firebase/php-jwt` reaches the vulnerable *function* unauthenticated but no principal below the platform operator can supply a key weak enough to meet the vulnerable *condition*, `symfony/yaml` is reachable only inside CI by a pull-request author who can already execute arbitrary PHP there, and `symfony/polyfill-intl-idn` is reachable only on a host without `ext-intl`. The adversarial pass moved seven advisories from not-reachable to reachable (five `guzzlehttp/guzzle` cookie advisories, one `symfony/polyfill-intl-idn`, one `symfony/yaml`-in-CI). **The single most urgent item is `symfony/http-foundation` CVE-2026-108082**: a single unauthenticated HTTP request carrying a crafted `Cache-Control` header drives a measured, large CPU cost (orders of magnitude above a benign request), and that cost is spent in `Request::capture()` at `public/index.php:17` — before `->handleRequest()`, so before the kernel, before `TrustProxies`, and before the `throttleApi('120,1')` limiter at `bootstrap/app.php:371` — it works on any URI including a 404 and `/up`, and the fix is a patch-level bump from `v7.4.3` to `v7.4.23` already permitted by `laravel/framework`'s `symfony/http-foundation: ^7.2.0`.

## 3. The reachable advisories, in severity order

### 3.1 `symfony/http-foundation` — CVE-2026-108082, HIGH, unauthenticated

**Flaw:** `HeaderUtils::split()` carries a nested-quantifier regex (`vendor/symfony/http-foundation/HeaderUtils.php:44-70`) whose token class `[^",=]+` matches spaces, so a whitespace run before a separator partitions exponentially.

**Call sites:** `vendor/symfony/http-foundation/HeaderBag.php:150-151` parses `Cache-Control` unconditionally inside `set()`, which `__construct()` calls for every header (`HeaderBag.php:32-36`, `:267-271`); reached from `public/index.php:17` → `Illuminate\Http\Request::capture()` (`vendor/laravel/framework/.../Http/Request.php:68-72`), which reconstructs the HeaderBag three times (`createFromBase()`: `new static(..., $request->server->all())` plus `headers->replace(...)`), a measured 2.9× amplifier.

**Reachability was confirmed in the review; the step-by-step reproduction (payload bytes, timing enumeration) is omitted from this committed defensive record. The advisory ID, call site, principal and fix below are what the owner needs to act.**

**Remediation:** `composer update symfony/http-foundation --with-dependencies` → **v7.4.23**, the max of all six per-advisory floors {7.4.19, 7.4.13, 7.4.23 ×4}. Do not stop at 7.4.19: the vendor's first ReDoS fix broke `HeaderUtils::split('foo bar', ' ')` in 7.4.19–7.4.20 and was completed in 7.4.21. Edge clamping of `Cache-Control` request-header size is a stopgap only.

### 3.8 `symfony/polyfill-intl-idn` — CVE-2026-46644. **Verdict corrected by the adversarial pass.**

**Original claim (incorrect):** "Gate 4 — the structural kill, and the one that holds under any PHP configuration… no CVE-2026-46644 payload can reach `IdnAddressEncoder.php:38`, on any host, intl or not," on the grounds that every divergent payload ends in `-` (6 of 13 probed labels diverged, all ending `-`) and egulias' `DomainHyphened` is a pure lexer rule.

**Correction:** the divergent *label* ends in `-`, but the *payload* need not put an ASCII `.` after it. UTS #46 §4.1 and the polyfill's own `Idn::process()` treat U+3002, U+FF0E and U+FF61 as label separators, while egulias' `EmailLexer` tokenises only ASCII `.` as `S_DOT`, so neither hyphen rule fires — `DomainPart.php:259-260` requires `isNextToken(S_DOT)` and `DomainPart.php:84-85` requires the domain to end in `-`.
